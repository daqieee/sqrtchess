# Alpha-Beta 引擎（新的基线对手）

这是根号棋的第二个 AI：一个「正统」的 Alpha-Beta 引擎。它取代原来的「吃子基线」，
成为新一版 AlphaZero 的**基线对手、陪练与评估锚点**。

## 一、需求对照

| 要求 | 实现 |
| --- | --- |
| Negamax + Alpha-Beta，深度 4 起步 | ✅ `AlphaBetaAI(depth=4)`，搜的是 negamax + alpha-beta |
| 评估函数 | ✅ 物质（按「能否移动」加权）+ 子数 + 机动性 + 死子威胁 |
| 迭代加深 | ✅ 从深度 1 逐层加深，可用时间上限中断（`time_limit`） |
| 着法排序 | ✅ 置换表着法 → 吃子（吃大子优先）→ 杀手着法 → 历史启发 |
| 置换表 | ✅ Zobrist 哈希 + 深度/上下界/分值/最佳着法（`TranspositionTable`） |
| Zobrist | ✅ 每个 (格点, 带符号大小) 一个随机数，含行棋方与无吃子进度 |
| 攻防交换分析（根号棋特有） | ✅ `analyze_exchange()`，见第三节 |

代码在 `sqrtchess/alphabeta.py`，注册名 `ab` / `ab2` / `ab4`（数字即深度）。

## 二、评估函数的想法

这个棋种里「棋子能不能动」只取决于它的大小能否写成两个整数平方和：

* 能移动（1、2、4、5、8、9、10、13……）：可以进攻、可以逃；
* **动不了（3、6、7、11、12、14、15……）**：永远动不了，既不能进攻也不能逃，只能被吃。

所以评估里：

~~~
分值 = Σ(己方子力) - Σ(对方子力)          # 能动的算满分，动不了的打 0.65 折
     + 3 × (己方子数 - 对方子数)          # 规则 7 与「吃光对手」都看子数
     + 0.15 × 己方合法着法数              # 机动性
     + 0.6 × Σ(能立刻吃到的对方死子大小)   # 白捡的
     + 0.4 × Σ(能立刻吃到的对方活子大小)   # 可能被还手，权重低
~~~

静态搜索（quiescence）里再用 SEE 剪掉亏本吃子，于是「吃子交换到底赚不赚」由搜索精确算出来。

## 三、攻防交换分析（需求里最看重的那条）

`analyze_exchange(game, 格点)` 回答四个问题：**这一格的攻防结束后归谁 / 那个子还能不能动 /
双方各损失多少 / 再补一个 1 或 2 能不能吃回并复活**。它会顺着 SEE 递归找出先手方最赚的一条吃子线，
再把结果摊开：

**例 1：吃了反而被自己卡死（先手方直接判负）**

~~~text
攻防焦点：f7（先手 w）
  结束后归属：w，该子大小 6，无法移动（死子）
  交换序列：5e5xf7
  这条线的净收益（含终局）：先手方 -99999.0，后手方 +99999.0
  实际吃到的子力差：+1.0（先手方视角）
  ⚠ 这条线走完对局直接结束：黑方胜（有一方无子可动，进入平局判定）……
  ⚠ 先手方走完变成「无子可动」，按规则 5/7 直接进入平局判定
~~~

**例 2：抢到一个子，但留下的是死子，对方可以用 1 吃回并复活**

~~~text
攻防焦点：e5（先手 w）
  结束后归属：w，该子大小 3，无法移动（死子）
  交换序列：1e4xe5
  这条线的净收益（含终局）：先手方 +2.0，后手方 -2.0
  继续吃回的选择：1e6xe5→4（可动）
  说明：抢下这一格的一方留下的是死子：既不能再进攻也不能逃，
        对方可以用小子吃回并把大小并过去，通常并不划算。
~~~

也就是说，需求里描述的「用 1 或 2 去取回对方动不了的大子」这件事，
引擎在评估、SEE 剪枝和这封报告里都能看见：1 + 3 = 4 是可以移动的，所以吃回之后立刻复活，
而只吃一口把自己变成 3、6、7 的一方反而被困死。

**SEE**：`see(game, move)` 返回这一步吃子的净收益（>0 赚，<0 亏）。
修复过一个关键 bug：终局分没有取反，导致「一步把对手吃光/卡死」这种赢棋着法被判成巨亏、
在静态搜索里被剪掉——修好之后引擎对吃子基线的胜率从 0.50 升到 0.83。

## 四、用法

~~~bash
# 命令行对局
python -m alphazero arena --a ab4 --b ab2 --games 8 --max-plies 200
python -m alphazero arena --a runs/az5/best.json --b ab3 --games 10 --sims 100

# 单局面评估与搜索
python -c "from sqrtchess import Game, make_ai; g=Game.new(); ai=make_ai('ab4'); print(ai.choose(g), ai.last.text())"

# 攻防分析
python -c "from sqrtchess import Game, make_ai; ai=make_ai('ab2'); print(ai.analyze(Game.new(), 'e5').text())"
~~~

图形界面「对局设置」里把对手选成 **Alpha-Beta 引擎** 即可与它对弈（深度在代码/命令行里给）。

## 五、实测

**速度**（中局 45 种着法，AMD 24 核，纯 Python）：

| 2 | 409 | 0.02 s |
| 3 | 5,539 | 0.22 s |
| 4 | 18,018 | 0.87 s |

**棋力**（`play_match`，交替先后手，上限 200 步）：

| 对局 | 得分率 | 平均大小差 |
| --- | --- | --- |
| Alpha-Beta(3) vs 吃子基线(4) | **0.833**（4 胜 0 负 2 和） | **+10.0** |
| Alpha-Beta(2) vs 随机走子 | ≥ 0.75（见测试） | — |

**测试**：`tests/test_alphabeta.py` 共 25 项，覆盖 Zobrist、置换表一致性、
SEE 的正负号、攻防报告的四个字段、迭代加深、限时、战术（白吃、拒吃、一步制胜）与实用对战。

## 六、局限与后续

* 纯 Python，深度 4 大约 0.9 秒/步；做陪练时用 `ab2`（0.02 秒/步），做锚点评估时用 `ab3`。
* 评估还是「物质 + 机动性」为主，没有做真正的局面理解（比如子力结构、王之类的概念在这个棋种里不存在）。
* 下一步可以加的：置换表的按代数淘汰（现在是满了清空）、吃子之外的静态搜索（比如「把对手逼到无子可动」的威胁）、
  以及把 `analyze_exchange` 的结论反过来喂给评估函数。

**最终模型（runs/az5/best.json）对战**：

| 对手 | 局数 | 得分率 | 平均大小差 |
| --- | --- | --- | --- |
| 吃子基线 | 14 | **0.607**（6 胜 3 负 5 和） | +0.7 |
| Alpha-Beta 深度 2 | 20 | 0.225（0 胜 11 负 9 和） | -7.8 |
| Alpha-Beta 深度 3 | 10 | 0.250（0 胜 5 负 5 和） | -22.2 |
| 归档的 az4 | 14 | 0.250（0 胜 7 负 7 和） | -26.0 |

**结论与诊断**：

1. **Alpha-Beta 确实是个强得多的基线**：它 0.833 打赢吃子基线，而这一版从头训练的
   AlphaZero（10 轮 / 43 分钟）只能赢吃子基线（0.607），打不过 ab2/ab3。
2. **策略损失在降（3.26 → 2.68）、物质差也在改善（-14 → +7）**，说明网络在学；
   但**赢不下来**——绝大多数对局以「100 步无吃子」或截断判定收场，价值信号非常稀疏。
3. **门控噪声导致了一次退化**：第 8 轮候选在 10 局门控里 0.750 被采纳，
   但换到 ab2 锚点上却是 0 胜 10 负。10 局的门控样本太小。
4. **搜索形态的差异才是关键**：ab2 = 全宽深度 2 + 吃子静态搜索（几乎穷尽所有着法），
   而 AlphaZero 这一侧是 100 次模拟的窄采样 MCTS。这个棋种战术密度高，
   窄采样在同等时间内明显吃亏。

**下一步建议**（按性价比排序）：

* **神经引导的 Alpha-Beta（混合）**：保留 Alpha-Beta 的搜索框架，把叶子评估换成
  「网络价值 + 物质项」。这样既保留了全宽搜索的战术精度，又能用上网络学到的局面判断——
  是这个棋种最值得一试的方向。
* 提高模拟次数到 400+，并把门控局数提到 20 局以上（降低误采纳）。
* 扩大网络（`--channels 48 --hidden 64`）并拉长训练到几小时。
